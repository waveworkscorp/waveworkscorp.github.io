# AEO content: work FAQ, post author and updated date

## 한국어 요약

- 결론: 작품 페이지에 "자주 묻는 질문" 절과 FAQPage 스키마를 넣고, 블로그 글에 작성자(홍마초)와 수정일을 보이게 함. 출시 글에 소제목을 넣음.
- FAQ는 두 출처를 씀: info 줄을 사이트 쪽 질문표로 바꾼 문답(사용자 선택 A) + site.json의 선택 `faq` 필드(사용자 선택 "둘 다").
- 작성자는 실명 대신 닉네임 "홍마초"(사용자 결정 2026-11-12). 영문 표기 Hongmacho는 Claude 판단.
- 범위 밖: Google FAQ 리치 결과(2023년부터 정부·보건 사이트 한정이라 기대하지 않음), 앱별 faq 문구 작성, 다른 글 소제목 손질.
- 되돌리기 어려운 부분: site.json 스키마에 `faq` 필드 추가(앱 저장소 5개가 읽는 계약). 선택 필드라 기존 앱은 그대로 동작.

## Why

Answer engines (AI search, assistants) quote pages that state questions and answers plainly, and trust content with a named author and a clear date. The site already ships SEO basics (canonical, sitemap, JSON-LD, 2026-11-12). This adds the answer-shaped content layer.

## Goals

1. Each work page has a visible FAQ section and matching `FAQPage` JSON-LD.
2. Each blog post shows an author and, when edited, an updated date; `BlogPosting` carries `author` (Person) and `dateModified`.
3. The launch post `2026-10-31-bus-loop-escape-launch.md` (ko and en) gets `##` headings.

Non-goals: Google FAQ rich results (Google limited them to government and health sites in 2023; value here is AI/assistant citation, not the SERP widget). Writing per-app `faq` copy (apps fill it later in their own sessions). Reworking headings of other posts.

Anti-goals: stating facts not already confirmed (site rule: only verified facts on work pages); exposing the owner's real name in the blog byline (user decision 2026-11-12).

## Constraints

- Work text source of truth is `apps/<id>/site/site.json`; the site copy `src/data/works.json` is generated by root `npm run site:sync` and never hand-edited (`docs/platform/site-sync.md`).
- Root repo (`scripts/site-sync/`) and site repo are separate git repos; commit separately.
- ko and en copy change together.
- No new dependencies.

## Approaches (FAQ source)

| | A. Site-side question table (picked) | B. `question` per info row in site.json |
|---|---|---|
| How | Site code maps each info label (10 known ko labels) to a ko/en question template with the work name | Each app writes the question text in its info rows |
| Touches | Site repo only | 5 app repos + sync script |
| Cost | New labels are skipped until added to the table (build warning) | Same questions repeated per app |

User picked A, plus the optional `faq` field for app-specific questions ("둘 다").

## Design

### 1. `faq` field in site.json (root repo)

- `scripts/site-sync/model.ts`: optional `faq: [{ q: {ko, en}, a: {ko, en} }]`, validated like `steps` (both languages non-empty), default `[]`.
- Sync writes it into `works.json` as `faq` only when non-empty (same style as other optional fields; check `plan.ts`).
- Tests in `scripts/site-sync/site-sync.test.ts`: valid faq passes through; missing `en` fails with a clear message; absent field yields no `faq` key.
- `docs/platform/site-sync.md`: add the row to the field table ("confirmed facts only", same rule as `info`).

### 2. Question table (site repo)

- `src/lib/faq-core.ts` (pure, `node --test`): `INFO_QUESTIONS: Record<koLabel, { ko: (name) => string; en: (name) => string }>` for the 10 labels in use: 지원 기기, 연령 등급, 광고, 앱 내 구매, 인터넷 연결, 지원 언어, 대상, 저장 위치, 공유 범위, 삭제 방법.
  Example: 광고 → ko `${name}에 광고가 있나요?`, en `Does ${name} have ads?`.
- `buildFaq(work, lang)`: authored `faq` first, then one entry per info row whose label is in the table (answer = the row value). Unknown labels are skipped and reported by a build-time `console.warn` from the page (not in the pure lib).
- `faqPageLd(url, entries)` added to `seo-core.ts`: `FAQPage` with `Question`/`acceptedAnswer` `Answer`.

### 3. Work page

- `WorkDetail.astro`: new section "자주 묻는 질문 / FAQ" near the bottom (after features and extra info boxes, before legal links), heading `h2`, each question `h3`, answer in a `p`, always expanded.
- The info boxes stay as they are. The derived answers repeat the info values in question form; accepted on purpose so answer engines get a Q&A block (Claude call, flagged for the user).
- `[slug].astro` (ko/en) pass `faqPageLd` alongside `workLd`; skip it when the list is empty.
- i18n strings: `faqHead` ko "자주 묻는 질문", en "FAQ".

### 4. Post author and updated date

- `src/data/blog.ts` (or i18n): `AUTHORS = { hongmacho: { name: { ko: '홍마초', en: 'Hongmacho' }, bio: { ko, en } } }` with default key `hongmacho`. Bio: one line, ko "웨이브웍스에서 게임과 앱을 만듭니다.", en "Makes games and apps at WaveWorks."
- `content.config.ts`: optional `author` (enum of AUTHORS keys, default `hongmacho`) and optional `updated` (same date format as `date`, must be >= `date`).
- `PostView.astro`: meta line becomes `date · (updated) · n min · author`; dates rendered in `<time datetime>`. A small author box (name + bio) above tags in the footer.
- `blogPostingLd`: `author` → `{ '@type': 'Person', name, url: <about page> }`; `dateModified` = `updated ?? date`. Publisher stays the Organization.
- `sitemap.xml.ts` uses `updated ?? date` for post `lastmod`.
- `blog-auto-write` skill (root `skills/blog-auto-write/`) is not changed now; frontmatter defaults keep new posts valid. Recorded as a follow-up for the skill to set `updated` when editing.

### 5. Launch post headings

- ko/en `2026-10-31-bus-loop-escape-launch.md`: add 3-4 `##` headings over existing paragraphs (e.g. 어떤 게임인가요 / 레벨과 부스터 / 지원 기기·언어와 광고 / iOS 버전) without changing facts; set `updated: 2026-11-12`.
