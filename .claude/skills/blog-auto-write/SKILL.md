# /blog-auto-write

입력: `$ARGUMENTS`

웨이브웍스 회사 사이트(Astro, `src/content/blog/`)에 글 한 편을 더한다. 뼈대는 hongmacho-blog의 `/auto-blog-write`이고, 회사 말투·사실 규칙·영어판·표지·승인 뒤 공개를 더했다. 설계: `docs/superpowers/specs/2026-10-31-blog-design.md` §5.

입력이 비어 있으면 §1-1대로 주제를 직접 고른다.

시작부터 미리보기(§11)까지 사용자에게 질문하지 않는다(사용자 지시 2026-10-31). 사용자는 실행 중 화면을 보고 있지 않으므로 질문으로 멈추면 일이 그대로 선다. 판단이 갈리면 Claude가 정하고 근거를 보고(§13)에 적는다. 사용자에게 묻는 것은 마지막 공개 승인(§13) 하나뿐이다. 개요가 정해지면 §3-3대로 한 번 알리지만 답을 기다리지 않는다.

## 0-0. 읽는 사람과 글쓴이 (사용자 지시 2026-11-06)

- 읽는 사람은 웨이브웍스가 누구인지, 무엇을 만드는지, 글에 나오는 앱·게임이 무엇인지 전혀 모르는 방문객이다. 글에서 처음 나오는 회사·작품·도구·내부 용어는 그 자리에서 한 문장으로 소개한다(예: 웨이브웍스는 모바일 게임과 앱을 만드는 회사, 오 마이 베이비는 아기 수유·수면을 한 손으로 기록하는 앱). 작품 소개는 `src/data/works.json`의 `tagline`·`about`에서 가져온다. 방문객이 모르는 내부 이름(저장소 폴더, 작업 ID, 문서 이름)은 풀어 쓰거나 뺀다.
- 소개는 이 글을 읽는 데 필요한 만큼만 한다. 회사는 한 문장, 작품은 이 글에 나오는 것만 이름과 한 줄 설명을 붙인다. 작품 전체 목록, 장르 나열, 일하는 방식 소개를 도입에 붙이지 않는다(사용자 지시 2026-11-06: 개발기 도입이 구구절절하다는 지적).
- 글은 글쓴이 본인이 올리는 글이다. "대표가", "사용자가"처럼 글쓴이를 제3자로 가리키지 않는다. 사람이 정한 일은 "우리가 ~로 정했습니다"처럼 우리를 주어로 쓴다(§6 공통의 주어 규칙 그대로).

## 0. 모든 글이 넘어야 할 기준 (사용자 지시 2026-10-31)

아래 셋을 모두 채워야 글을 낸다. 주제 고르기부터 마지막 대조까지 이 기준으로 판단하고, 셋이 부딪히면 적힌 순서를 따른다.

1. 마케팅·브랜딩에 도움이 되는가. 읽은 사람이 작품을 받아 보고 싶어지거나 웨이브웍스를 믿게 되어야 한다. 기술 글도 "이 회사는 이런 점까지 챙긴다"가 남게 쓴다. 내부 구현 세부(키 이름, 규칙 문법, 함수 이름)는 그 목적에 필요한 만큼만 쓴다.
2. 사람이 쓴 글처럼 읽히는가. 구체적인 날짜·장면·숫자로 말하고, AI 문체 흔적(§6 금기, 3박자 나열, 같은 어미 반복, 매끈한 일반론)이 없어야 한다.
3. 읽기 쉬운가. 처음 보는 사람이 한 번에 따라오게 쓴다. 전문 용어는 풀어 쓰거나 빼고, 문단은 짧게, 한 문단에는 한 가지만 담는다. 표·목록·그림은 문장보다 빨리 읽힐 때만 쓴다.

판정에는 글 속 근거를 붙인다(§9-3, 사용자 지시 2026-11-06).

- 글이 다루는 문제마다 해결 결과와 남은 한계를 짝지어 쓴다.
- 작업·커밋·테스트 개수는 규모 정보로만 쓰고 개선 효과로 쓰지 않는다. 효과 수치는 같은 대상·조건·기준일로 비교하고, 재지 않은 효과는 "측정 전"이라고 적는다.
- 신뢰를 뒷받침하는 판단이나 검증 사례를 하나 이상 싣는다.
- 남길 믿음 → 그 믿음을 보여 주는 선택 → 실제 검증 → 남은 한계를 이어서 확인한다. "꼼꼼하다" 같은 평가어를 지워도 독자가 그 선택을 확인할 수 있어야 한다. 예상한 독자 반응과 실제로 관측한 반응은 구분해 적는다.

## 1. 주제·문체 틀·제목 정하기

주제, 문체 틀, 제목은 Claude가 정하고 사용자에게 묻지 않는다(사용자 지시 2026-10-31). 정한 근거는 보고(§13)에 적는다.

### 1-1. 주제

- 입력에 주제가 있으면 그 주제를 쓴다.
- 없으면 후보를 모아 하나를 고른다. 후보는 작품 `docs/STATE.md`의 최근 출시·업데이트, 작품 git log의 최근 큰 변경, `../../docs/portfolio.md`의 단계 변화, `src/data/pages.ts` 연혁에서 찾는다. `ls src/content/blog/ko/`로 이미 쓴 글과 겹치는 주제는 뺀다.
- 후보마다 §0-1(이 글이 작품이나 회사에 어떤 믿음을 남기는지)을 따져 가장 큰 쪽을 고른다.
- 주제 한 문장, 다룰 작품 slug, 각도(출시 소식, 업데이트, 제작 회고, 실험기, 팀 문화)를 정한다.

### 1-2. 문체 틀

누가 무엇을 하려고 읽는 글인지로 고른다. 카테고리로 정하지 않는다.

| 틀 | 읽는 사람 | 예 |
|---|---|---|
| 마케팅(§6-A) | 받을지, 해 볼지 정하는 플레이어·사용자 | 출시 소식, 새 기능 업데이트, 이벤트 |
| 기술(§6-B) | 만든 과정과 판단이 궁금한 사람 | 회고, 제작기, 엔진·도구 결정, 일하는 방식 |

news 카테고리라도 기술 결정을 설명하는 글이면 기술 틀을 쓴다. 기술 틀도 작품의 잠재 사용자가 읽을 수 있게 쓴다(§0).

### 1-3. 제목

§3-2 조사를 마친 뒤 정한다. 사람이 쓴 한국 회사 블로그 15편을 세어 보니 "~했습니다"로 끝나는 제목은 0편이었고, 명사구·질문·"A: B" 부제형이 대부분이었다(2026-10-31 조사, 중앙값 약 25자).

- 제목을 "~했습니다", "~기로 했습니다" 같은 완결 문장으로 짓지 않는다. 예외는 출시 소식의 "~나왔습니다" 하나다.
- 모양은 명사구("~ 제작기", "~ 회고"), 질문("~할까"), "A: B" 부제형, 숫자형("10분에서 10초로") 가운데서 고른다.
- 서로 다른 모양으로 후보 5개를 만들고 §0 순서로 하나를 고른다. 후보와 고른 이유는 보고에 적는다.
- 작품 글은 제목에 작품 이름을 넣는다. 25자 안팎, 최대 35자.
- "~ 이후 바꾼 것", "~한 이유"처럼 글 내용을 요약하는 꼬리는 붙이지 않는다.

### 1-4. 입력 옵션

- "한국어만"이 있으면 영어판을 만들지 않는다.

## 2. 카테고리

| 값 | 이름 | 쓰는 글 | 기본 분량(한국어) |
|---|---|---|---|
| `news` | 소식 | 출시, 업데이트, 회사 소식 | 1,000~2,000자 |
| `culture` | 문화 | 일하는 방식, 도구, 회고 | 2,000~4,000자 |
| `making` | 제작기 | 게임·앱을 만든 과정, 기술 결정 | 4,000~6,000자 |

분량은 예상 범위이고 합격 조건이 아니다. 기술 글(culture·making)은 §6-00의 개념 수준 기준(본문 3,000~4,500자)이 위 표보다 앞선다. 절마다 독자 질문에 답하는 데 필요한 만큼 쓰고, 사용자가 더 자세히 쓰라고 요청하면 기본 분량보다 그 요청이 앞선다. §3-2에서 조사한 같은 주제 글의 길이도 참고한다.

## 3. 사실 모으기

수치·날짜·평점·출시 여부·기능은 아래에서만 가져온다. 근거가 없으면 다른 출처를 더 찾고, 그래도 없으면 문장을 뺀다. 쓴 사실마다 출처를 적어 두었다가 보고에 넣는다.

| 출처 | 쓰는 내용 |
|---|---|
| `../../apps/<id>/site/site.json` | 이름, 한 줄 소개, 기능, 지원 기기·언어, 광고·구매, 스토어 |
| `../../apps/<id>/docs/STATE.md` | 출시일, 버전, 진행 단계 |
| `src/data/pages.ts` 연혁 | 회사 연혁 |
| `../../docs/portfolio.md` | 작품 목록과 단계 (STATE와 다르면 STATE를 따르고 보고에 적음) |
| `git -C ../../apps/<id> log --format='%ad %s' --date=short` | 일화: 날짜별로 한 일, 다시 만든 일, 바꾼 결정. 커밋 메시지에 적힌 것만 쓴다 |
| `../../apps/<id>/docs/superpowers/specs/`, `docs/plan/`, `docs/design/` | 설계 이유, 검토한 대안과 버린 이유, 사용자가 정한 결정과 날짜 |
| `../../apps/<id>/docs/log/`, `docs/ROADMAP.md`, `docs/wiki/` | 작업 기록: 막힌 곳, 리뷰에서 나온 문제와 고친 방법, 테스트 수, 남은 일 |
| `git -C ../../apps/<id> log --format='%ad %s' --date=iso` | 작업 시각(같은 날 몇 시에 무엇을 했는지) |
| 사용자 입력 | 사용자가 요청에 직접 적은 사실 |

- 사이트의 작품 slug는 `src/data/works.json`에 있다. `works`에는 여기 있는 값만 넣는다.
- 매출, 다운로드 수, 지표는 사용자가 준 값만 쓴다.
- 플랫폼·사이트·도구처럼 회사 차원의 주제는 해당 저장소(루트 `docs/`·`work/`, 사이트)의 문서·작업 기록·코드·실행 결과도 출처로 쓴다. 작업 정본(`docs/work`)이 있으면 생성된 로드맵보다 정본을 먼저 읽는다(사용자 지시 2026-11-06, Codex 리뷰).
- 사실마다 기준일과 상태(계획 / 구현 / 검증 / 운영)를 구분한다. 설계서와 커밋 제목만으로 현재 동작이나 효과를 단정하지 않고, 실행 결과로 확인하거나 "설계 기준"이라고 밝힌다. 실행 결과는 가져온 시점을 본문에 적는다.

### 3-1. 이유와 일화 찾기

사실만 모은 글은 설명서처럼 읽힌다. 이유, 버린 대안, 막힌 장면, 다시 한 일은 앱의 설계서·작업 기록·커밋에 남아 있으므로 쓰기 전에 그곳을 끝까지 읽는다.

- 설계서의 "접근 비교", "결정", "반목표" 절과 작업 기록의 리뷰 지적·수정 내역을 먼저 본다. 글에 깊이를 주는 내용이 대부분 여기 있다.
- 읽을 문서가 많으면 서브 에이전트(`model: opus`)에 넘겨 사실 목록(문장, 출처 파일)만 받는다(사용자 지시 2026-11-06: 리서치는 Opus).
- 문서에 적힌 이유만 쓴다. 문서에 없는 감정이나 속마음("그때 고민이 많았습니다")은 지어내지 않는다.
- 분 단위 시각과 커밋·작업 개수는 선택이나 실패의 이유를 설명할 때만 본문에 두고, 작업량을 자랑하는 값은 뺀다. 도입에는 쓰지 않는다(2026-11-06, Codex 문체 진단: 현지화·동의 화면·9일 회고의 도입이 속도부터 보여 줌).
- 사실이 모자라면 주제를 좁히거나 분량을 줄인다. 사용자에게 묻지 않는다.

### 3-2. 같은 주제 글 조사 (글마다, 생략 금지)

이 글과 주제·각도가 같은 다른 회사·매체·개인의 글을 읽고, 쓰는 방식과 다루는 내용, 형식을 정한다. 조사에서 나온 형식은 §6의 기본값보다 앞서지만, 사용자 요청에 적힌 구조·형식 요구(§3-3)보다는 뒤다.

- 서브 에이전트(`model: opus`)에 WebSearch·WebFetch로 같은 주제 글 6~10편을 찾게 한다. 검색어는 이 글의 주제로 만든다(예: "퍼즐 게임 출시 공지", "1인 개발 첫 게임 회고", "Unity 전환 후기"). 한국어 글을 절반 넘게 넣고 영어 글을 섞는다. 회사 블로그, 커뮤니티 공지, 개인 개발 블로그를 섞는다.
- 받아 올 것(글마다 URL을 붙인다):
  - 쓰는 방식: 첫 문단을 무엇으로 여는지, 어미와 문장 길이, 읽는 사람을 부르는 방식, 끝맺는 방식
  - 내용: 같은 주제 글이 공통으로 다루는 항목과 읽는 사람이 기대하는 정보(출시 글의 지원 기기·가격, 회고 글의 실패와 수치 등). 이 글에 빠진 항목은 §3 출처에서 찾고, 없으면 그 항목을 뺀다.
  - 형식: 소제목 유무와 개수, 섹션 순서, 목록·표 사용, 그림 수와 위치, 링크 위치, 길이
  - 제목·소제목 원문: 글마다 그대로 모으고, 모양(명사구, 질문, 부제형, 완결 문장)별로 센다. 분포는 참고만 하고 그대로 따르지 않는다. 채택하는 형식마다 이 글의 독자 질문을 더 잘 풀어 주는 이유를 보고에 적는다(§1-3, §6 소제목).
- 검색어에는 대기업 기술 블로그 말고 인디 게임 개발기, 앱 업데이트·기능 소개 글을 따로 넣는다.
- 여러 글에서 겹치는 점을 3~6줄로 정리하고, 이 글의 개요로 옮긴다. 개요에는 소제목 여부와 순서, 섹션(문단)마다 넣을 사실, 길이, 제목 방식을 적는다. 개요에서 사실이 비는 칸은 §3-1 출처를 다시 뒤져 채운다.
- 다른 글의 문장, 사실, 수치는 가져오지 않는다. 문장을 그대로 옮기거나 15단어 넘게 인용하지 않는다.
- 조사 결과 요약과 참고한 URL은 보고(§13)에 넣는다. 저장소에는 남기지 않는다.

### 3-3. 집필 전 요구 정리와 개요 (본문 쓰기 전, 생략 금지)

2026-11-06 개발기 글이 두 번 반려됐다. 요청의 "기술적인 문서"가 주제 한 줄로 줄어들고, 문체·분량·제작 일화가 글의 모양을 정했기 때문이다. 본문을 쓰기 전에 아래를 적는다.

- 독자(누구이고 이미 아는 것은 무엇인가), 읽는 목적, 글 전체가 답하는 핵심 질문 하나, 읽고 남길 믿음(§0-1)
- 주 독자 한 부류와 보조 독자를 정한다. 독자는 플레이어·사용자, 개발자·인디 제작자, 협업·채용 관심자 세 부류이고 블로그 전체에서는 모두 다루지만, 한 글에서 같은 깊이로 모두를 만족시키지 않는다. 부류마다 읽고 풀고 싶은 질문을 한 문장씩 적고, 고른 근거를 보고한다. 보조 독자는 도입과 결과 요약에서 따라오게 하고, 주 독자용 깊이는 본문에 둔다.
- 사용자 필수 요구: 요청에 직접 적은 구조·포함할 자료·상세 정도·어조. 요청 문장을 그대로 옮겨 적는다.
- 다루지 않을 범위
- 각 필수 요구를 개요의 절과 증거(캡처, 코드, 표, 수치)에 연결한다. 연결하지 못한 요구가 있으면 쓰기 전에 자료를 더 모은다.
- §3-2 조사는 형식 참고일 뿐 이 요구를 덮어쓰지 않는다. 충돌하면 사용자 요구가 이긴다.
- 개요가 정해지면 제목, 핵심 질문, 절별 증거, 제외 범위를 진행 중 안내로 한 번 알린다. 답을 기다리지 않고 이어 간다.

## 6. 본문 (한국어)

쓰기 전에 `voice-examples.md`(이 스킬 폴더)를 읽는다. 틀마다 고친 문단과 고치기 전 문단이 짝지어 있다.

공통:

- 어미는 두 틀 모두 합니다체. 해요체는 써 봤다가 문체가 어색해져 되돌렸다(사용자 결정 2026-10-31). "~입니다"로 끝나는 설명문이 이어지지 않게 동작을 쓰는 동사("만들었습니다", "바꿨습니다")로 끝을 바꿔 가며 쓴다. 이모지와 느낌표는 쓰지 않는다(사용자 결정 2026-10-31).
- 주어는 "우리" 또는 "웨이브웍스". 개인 1인칭과 반말은 쓰지 않는다. "대표가", "사용자가" 같은 제3자 표기도 쓰지 않으며, 예문과 윤문 결과(§9)에도 같은 기준을 적용한다(§0-0, 2026-11-06 결정으로 "우리" 유지).
- 소제목 유무와 개수, 길이, 목록·표 사용, 링크 위치는 §3-2 개요를 따른다. 조사 결과가 갈리면 기본값을 쓴다: 기술 틀은 첫 소제목 "개요"(아래 §6-B)와 h2 4~7개, 마케팅 틀은 소제목 없이 문단 4~7개.
- 문장을 뚝뚝 끊지 않는다(사용자 지적 2026-11-06). 원인과 결과, 이유와 조치, 앞 문장의 설명과 뒤 문장의 사실은 "~는데", "~고", "~기 때문에", "~해서", "~므로" 같은 연결 어미로 한 문장에 잇는다. 한 문단은 두세 문장이 기본이고, 문장 하나가 한 가지 사실만 말한 채 끝나는 일이 세 번 이어지면 합쳐서 다시 쓴다. 문장이 한 줄 반(공백 포함 약 80자)을 넘으면 그때 나눈다. 같은 어미가 세 문장 넘게 이어지지 않게 한다.
- 매번 같은 틀로 끝내지 않는다. "문의하기로 보내 주세요"를 모든 글 끝에 붙이지 않는다.

소제목(사용자 지적 2026-10-31: 소제목이 모두 "~습니다" 문장이라 AI가 쓴 티가 남):

- 본문 어미를 소제목에 옮기지 않는다. 명사구("휴대폰에만 있던 기록", "남은 일")와 짧은 질문("언제 물어볼까")을 주로 쓰고, "~습니다"로 끝나는 소제목은 한 편에 하나까지만 둔다.
- 소제목은 그 절의 결론이 아니라 무엇을 다루는지를 단다. "거절해도 잃는 건 없습니다"보다 "[나중에]를 누르면"이 낫다.
- 같은 접두어나 같은 틀을 이어 쓰지 않는다("10월 3일, ~", "10월 4일, ~"처럼 날짜를 매번 앞에 두지 않음). 날짜는 본문 첫 문장에 둔다.
- 15자 안팎으로 짧게 쓴다.
- 쉬운 말로 단다. "막혔던 곳", "~를 어디에 둘까", "정본", "지문으로 비교합니다"처럼 말을 돌리거나 비유로 지은 표현은 AI 티가 난다는 지적을 받았다(사용자 지시 2026-11-06). "문제점", "해결 방법", "결과", "원본", "해시값"처럼 평범한 말을 쓴다. 비유로 만든 용어는 본문에도 쓰지 않는다.
- 목차만 읽어도 각 절이 무엇을 다루는지 같은 정도로 구체적이어야 한다. "봇 테스트 294/300"처럼 구체적인 소제목 옆에 "결과", "남은 일"만 있으면 대상을 더해 고른다.

### 6-00. 집필 모델과 기술 글의 상세 수준 (사용자 지시 2026-11-06)

모델 분담(사용자 지시 2026-11-06): 글 작성(한국어 본문·영어판)은 Fable, 리서치(사실 수집 §3-1, 같은 주제 글 조사 §3-2)는 Opus, 빌드·대조·커밋은 Claude 메인이 맡는다. 바꾸려면 이 줄과 §3-1·§3-2·아래 첫 항목을 함께 고친다.

- 한국어 본문과 영어판 집필은 `model: fable` 서브 에이전트에 맡긴다. 같은 브리프로 Opus와 Fable에게 개발기를 새로 쓰게 비교했고, 사용자가 Fable이 확실히 더 잘 쓴다고 판단했다. 에이전트에는 사실 목록(출처 파일), §0·§0-0·§6-0·§6-B, `voice-examples.md`, 이 절의 상세 수준 규칙을 준다. Claude(메인)는 사실 수집, 빌드, 대조, 커밋을 맡고 집필 결과를 §9-3으로 점검한다.
- 기술 글의 상세 수준은 개념 수준이다. 구성은 "기존에 이렇게 했다 → 이런 문제가 있었다 → 이렇게 개선했다 → 이만큼 좋아졌다 → 그래서 지금 이렇게 운영한다"로 한다. 구현 세부(필드명 목록, 규칙·오류 이름, 거부 사유, 잠금·충돌 절차, 이관 단계, 테스트 개수, 명령어 나열, 개정 이력)는 쓰지 않고, 개선의 핵심 아이디어를 이해하는 데 필요한 것 하나씩만 남긴다. 사용자가 구현 세부를 직접 요청하면 그 요청이 우선하고, 그때도 본문은 개념 수준으로 두고 세부는 접는 절이나 별도 글로 나눈다.
- 기술 글 분량의 기본은 본문 3,000~4,500자다. 8,000자를 넘기면 세부를 더 쓴 것이 아닌지 점검한다(같은 날 사용자 평: 두 집필본 모두 "너무 자세한 이야기를 쓴다").
- "좋아진 점"에는 근거가 있는 변화만 쓴다. 측정하지 않은 효율 수치를 만들지 않고, 재지 않은 효과는 "측정 전"이라고 쓴다.

### 6-0. 말투: 실무자가 독자에게 설명한다 (사용자 지시 2026-11-06, 모든 글·두 언어에 적용)

글쓴이는 이 일을 직접 하는 사람이다. 기록과 로그를 옮겨 적는 보고서 시점이 아니라, 하는 일을 독자에게 설명하는 말투로 쓴다. 기본 흐름은 문제 → 필요 → 하는 일 → 얻는 이점이다.

- 묘사하지 말고 쓸모를 말한다. 기능과 화면은 모양(카드 한 장, 칩 9개, 막대, 오른쪽 패널)을 읽어 주지 않고, 그것으로 무엇을 할 수 있는지 쓴다("~를 확인할 수 있습니다"). 모양은 캡션이 맡는다.
- 평범한 업무 어휘를 쓴다. "문제가 있어", "꼭 필요합니다", "관리하기 어려워졌습니다"처럼 현업에서 쓰는 말이다. 이야기를 꾸미는 말은 쓰지 않는다. 예: 통째로, 버티지 못했다, 바닥나다, 흔들리다, 사고를 냈다, 갈아엎다, 구멍.
- 사실에 없는 수식어와 방식을 붙이지 않는다. "손으로 적던", "나중에 사람이 옮겼다"처럼 문서·로그·커밋에 없는 주체나 방법은 글의 신뢰를 깎는다. 수식어마다 출처가 있는지 확인하고, 없으면 뺀다.
- 내부 표기와 코드 기호를 제목·소제목·설명 문장에 쓰지 않는다. `[x]`, 작업 ID, 필드명, 파일 이름은 독자에게 낯설고 어색하게 읽힌다(사용자 지적 2026-11-06: `[x]`가 제목과 본문에 들어가 어색하다). "체크 표시", "완료 표시"처럼 말로 쓴다. 실물을 보여 줄 때만 코드 블록이나 표 안에 인용하고, 문장에서는 그 표기를 설명하지 않고 말로 풀어 쓴다.
- 글에서 우리가 만든 것을 "작품"이라고 부르지 않는다. 어색하다는 지적을 받았다(사용자 지시 2026-11-06). 게임이면 "게임", 앱이면 "앱", 둘을 함께 가리키면 "앱과 게임"이나 "프로젝트"로 쓴다. 이 스킬 안의 "작품"과 `works.json`의 이름은 내부 용어라서 본문과 에이전트 브리프의 문장에 옮기지 않는다. 집필 에이전트에게 브리프를 줄 때도 "작품" 대신 "앱·게임"을 쓰고, 교정 단계에서 `grep -n 작품 <파일>`로 남은 곳을 확인한다.
- 날짜와 시각은 시점이 이해에 필요할 때만 쓴다. 작업한 날, 화면을 캡처한 시점, 기준일은 기본으로 쓰지 않는다. 쓰려면 이 글에서 왜 필요한지 말할 수 있어야 한다(출시일, 기한, 변경 전후 비교는 필요한 경우).
- 도구를 쓰는 일은 직설로 쓴다("Claude Code와 함께 짜는데" 대신 "Claude Code로 개발을 진행하는데"). 도구의 한계를 말할 때는 그 한계 때문에 무엇이 필요해졌는지까지 한 문장으로 잇는다.
- 같은 기준을 영어판에도 적용한다. 묘사 대신 기능("you can see ..."), 꾸밈 은유 대신 평범한 업무 어휘를 쓴다.

### 6-A. 마케팅 틀 (news)

플레이어(사용자)가 읽는 글이다. 아래 형식 항목은 §3-2 조사가 다른 형식을 가리키면 조사를 따른다.

- 짧은 문장. 읽는 사람을 "여러분"으로 부르지 않는다. 플레이 상황을 쓸 때는 site.json이나 앱 문서에 근거가 있는 상황만 쓴다.
- 회사 소개로 시작하지 않는다. 기본은 "나왔습니다" 소식과 받기 링크로 첫 문단을 여는 것이다. 회사 이야기는 뒤에 짧게.
- 기능 목록보다 해 보면 어떤지를 쓴다. 기능은 장면 속에 녹인다.
- 만든 이유나 의도를 한두 문장 넣는다(설계서·기획서에 적힌 것만). 감사 인사는 고마운 대상이 실제로 있을 때만.
- 지원 기기·언어·광고·구매 같은 확인 사항은 한 곳에 모은다.
- 끝은 다음 소식이나 의견 요청처럼 읽은 사람이 할 일로 닫는다.

### 6-B. 기술 틀 (culture, making)

만드는 사람이 읽는 글이다. 아래 형식 항목은 §3-2 조사가 다른 형식을 가리키면 조사를 따른다.

- 기본 틀은 기존 방식과 문제 → 해결 원리와 선택 이유 → 검증 결과와 남은 한계 → 현재 운영 방식이다. 시간순은 원인과 결과를 설명하는 데 필요할 때만 쓴다. 사용자가 다른 틀을 요청하면 그 틀이 먼저다(2026-11-06, Codex 리뷰).
- 절마다 독자 질문 하나와 그 답을 증명하는 최소 증거(숫자, 날짜, 커밋 기록, 코드, 표, 화면)를 둔다. 기술적 깊이는 원인·동작·실패 조건·검증 설명으로 판단한다. 질문에 답하지 않는 날짜·필드·오류 이름 나열은 줄인다.
- 기술 글은 맨 위에 "## 개요" 소제목을 두고, 그 아래에 이 글이 다루는 문제, 바꾼 것, 결과를 2~3문장으로 요약한다(사용자 지시 2026-11-06: 기술 문서는 위에 개요 소제목이 있는 것이 좋다). 개요만 읽어도 글의 결론을 알 수 있어야 하고, 결과 화면이 있으면 개요 바로 아래에 둔다. 소제목은 "개요" 하나만 이 이름을 쓰고, 나머지는 §6 소제목 규칙을 따른다. 마케팅 틀(news)에는 쓰지 않는다.
- 도입(개요 본문)은 인사 대신 이 글이 다루는 문제와 바꾼 결과를 2~3문장으로 잇고, 회사 소개는 그 문제를 이해하는 데 필요한 한 문장만 넣는다(§0-0). 작품은 이 글에 나오는 것만 첫 등장 때 한 줄로 설명한다. 낯선 기술 용어는 역할을 먼저 설명한다. 숫자나 날짜가 든 장면은 그 문제를 보여 줄 때 쓴다.
- 결과 화면이 있는 글은 도입 바로 뒤에 그 화면을 먼저 보여 주고, 설명은 그다음에 한다. 독자가 무엇을 만든 글인지 먼저 보게 한다(2026-11-06).
- 본문은 주 독자의 핵심 질문 순서로 구성한다. 구현 항목마다 같은 비중으로 쓰지 않는다. 재현용 코드, 전체 필드 목록, 오류·응답 코드 목록, 명명 이력은 독자의 질문에 필요한 하나만 남기고 나머지는 뺀다. 빼기 아까운 자료는 접는 절(`<details>`)로 옮기되 사이트가 그 태그를 제대로 보여 주는지 미리보기로 확인하고, 안 되면 별도 글로 나눈다. 상세함은 자료를 보존하는 방식으로 채우고 본문을 늘려서 채우지 않는다.
- 이미 설명한 원칙을 다음 일화 끝에서 "그래서 지금은 ~합니다"로 되풀이하지 않는다. 적용 결과가 아직 없으면 방침을 바꿨다는 데까지만 쓴다.
- 틀린 판단과 다시 한 일을 숨기지 않는다. 무엇이 틀렸고 왜 바꿨는지 우리 결정으로 쓰고, 실패마다 근거(횟수, 시각, 전후 수치)를 하나씩 붙인다(설계서·작업 기록·커밋 근거).
- 끝에서는 아직 못 한 것(작은 성과, 없는 지표)을 인정하고 다음 행동으로 닫는다.
- 원칙은 그 원칙이 생긴 일화 바로 뒤에 둔다. 원칙만 따로 나열하지 않는다.
- 보고서처럼 사실을 나열하지 않고, 처음 읽는 사람에게 설명하듯 문장을 잇는다. 한 문단에 같은 사실을 두 번 쓰지 않는다(예: "1인 회사입니다. 사람은 한 명이고"). "A는 X가, B는 Y가, C는 Z가"처럼 같은 틀을 세 번 이어 붙이지 않는다.

### 6-C. 그림

- 표지는 글 상세 첫머리에 자동으로 나온다. 본문에 다시 넣지 않는다.
- 본문 그림은 설명에 필요한 증거로 정한다. 화면 구성·동작은 실제 캡처, 데이터·구조는 코드 조각이나 표, 전후 비교는 표를 우선한다. 같은 화면을 반복하지 않고 그림마다 글 속 역할이 있어야 한다. 그림이 필요 없는 글이면 0장도 괜찮다(2026-11-06: 기술 글에서 장수 제한을 풀고 필요한 증거 기준으로 바꿈).
- 그림 앞이나 뒤 문장이 그림 속 내용을 말해 준다. alt는 필수이고 화면에 보이는 것을 쓴다.
- 작품 화면은 사이트 스크린샷 `/works/<id>/shots/{ko,en}-N.jpg`를 쓰고(영어판은 en), alt는 site.json의 `captions`를 바탕으로 쓴다.
- 실제 화면이나 구현을 설명하는 자리에는 캡처를 쓴다. 생성 삽화로 구현의 증거를 대신하지 않는다. 캡처할 수 없으면 그 한계를 본문에 밝힌다. 캡처는 읽기 전용으로 이동만 하고(상태를 바꾸는 버튼을 누르지 않음), 공개 점검은 §9-4를 따른다. 캡처 파일은 `src/assets/blog/<이름>/`에 두고 2배 해상도로 찍어 가로 1800px JPEG로 줄인다.
- 분위기만 전하는 장면에 한해 Codex 삽화를 `src/assets/blog/<이름>/<파일>.jpg`에 두고 `../../../assets/blog/<이름>/<파일>.jpg`로 건다(§8 절차, 1600×900, 글자 없는 그림).

### 6-D. 게임·앱 출시 글

어떤 게임(앱)인지 처음 듣는 사람도 알 수 있게 쓴다. site.json의 `about`, `steps`, `features`, `captions`, `info`를 모두 읽고 아래 내용을 빠짐없이 담는다. 섹션으로 나눌지 문단으로 이을지는 §3-2 개요를 따른다.

- 무엇을 하는 게임인지, 재미가 어디서 나오는지 (about)
- 플레이 순서 (steps, 첫 스크린샷)
- 진행하며 달라지는 것과 특수 요소 (features, 해당 스크린샷)
- 막혔을 때 쓰는 도구와 보상 (features, captions)
- 받기 전에 확인할 것 (info: 기기, 등급, 광고, 구매, 언어)

site.json에 없는 규칙·수치·기능 설명은 지어내지 않는다. 부스터처럼 이름만 있는 요소는 이름만 쓴다.

금기 문장(나오면 지우고 다시 씀):

- "안녕하세요", "여러분", "오늘은", "이번 글에서는", "~에 대해 알아보겠습니다"
- "정리하면", "결론적으로", "In conclusion"
- 헤더 "맺음말", "결론", "마치며"
- 이모지, 감탄 연발, "X가 아니라 Y" 대비
- 예고형: "~한 조건이 하나 있습니다. ~라는 것입니다", "이유는 두 가지입니다". 조건이나 이유를 바로 쓴다.
- 글을 설명하는 메타 문장: "~을 순서대로 적었습니다", "~ 과정을 정리했습니다", "왜 이렇게 만들었는지 적어 둡니다"

윤문은 여기서 돌리지 않는다. 영어판과 표지까지 끝낸 뒤 §9에서 한꺼번에 한다.

## 7. 영어판

- 한국어판을 옮겨 쓴다. 윤문은 §9에서 한다.
- 문체 틀을 따른다. 마케팅 틀은 "you"로 부르는 가볍고 짧은 문장으로 쓴다. 기술 틀은 한국어판의 논리와 사실을 그대로 두고 "we" 주어의 영어 어순으로 다시 쓴다. 한국어 문장을 순서대로 옮기지 않는다. 예제 속 한국어(표, 코드)는 바로 뒤에 영어로 풀어 준다.
- 한국어판과 주체(누가), 시점(언제), 조건, 약속의 강도가 같은지 문장마다 대조한다.
- 작품 이름은 site.json의 `name.en`을 쓴다.
- 영어판만 있는 글은 빌드가 막으므로 한국어판을 먼저 둔다.

## 8. 표지

1. `codex-delegation` 스킬로 한도를 확인하고 한 줄로 알린다. 한도가 막히면 표지 없이 진행한다.
2. `cover-prompt.md`의 문장에 주제 장면을 채우고 마스코트 참고 이미지(`-i public/img/mascot-about.png`)를 붙여 `codex exec`로 이미지를 만든다. 로봇은 그리지 않는다.
3. 결과는 `~/.codex/generated_images/<세션>/`에 생긴다. `cp`로 가져온다(`mv`·`rm` 금지, 원본은 남김).
4. 폴더를 만들고 sharp로 1600×900에 맞춰 자른다.

```bash
mkdir -p src/assets/blog/<이름>
node -e "require('sharp')(process.argv[1]).resize(1600,900,{fit:'cover'}).jpeg({quality:85}).toFile(process.argv[2])" <원본> src/assets/blog/<이름>/cover.jpg
```

5. 그림 안에 글자가 들어갔으면 한 번 다시 만든다. 그래도 있으면 표지 없이 진행한다.
6. 실패하면 cover 없이 진행하고 보고에 "표지 미생성"과 이유를 적는다. 목록은 카테고리 색 상자로 자리를 채운다.

## 9. 문체 교정 (마지막 단계, 생략 금지)

글을 다 쓰고 표지까지 정한 뒤, 빌드 전에 반드시 돌린다. 앞 단계에서 이미 다듬었어도 건너뛰지 않는다. 기준은 `writing-pipeline` 스킬 표(전역 문체 규칙)의 블로그 행이다. 대상은 본문, 소제목, frontmatter의 title·excerpt·coverAlt다. 윤문 스킬은 소제목을 따로 보지 않으므로 소제목은 §9-3에서 직접 검사한다.

### 9-1. 한국어판

윤문 스킬은 글 하나에 하나만 쓴다. 순서는 윤문 → `grammar-checker` → `style-guide`.

| 카테고리 | 윤문 |
|---|---|
| making, culture (개발 후기·회사 이야기) | `humanizer-ko` |
| news (출시 공지·업데이트처럼 수치·기능을 약속하는 글) | `humanize-korean` 정밀(heavy) 모드. 입력을 스크래치패드에 복사해 그 폴더에서 돌린다(저장소에 `_workspace/`를 만들지 않음) |

- 검사 스킬은 고쳐 쓰지 않는다. 걸린 곳만 고친다.
- 윤문 스킬이 변경률 경고로 확인을 요청하면 사용자에게 넘기지 않고 보수적으로 다시 돌린다.
- 블로그 말투로 맞춘다: 두 틀 모두 합니다체, 주어는 "우리"·"웨이브웍스". 음슴체·반말·개인 1인칭이 섞였으면 그 틀의 어미로 되돌린다. 윤문 스킬이 어미를 바꾸면 되돌린다.

### 9-2. 영어판

순서는 `slopbeth` → textlint write-good. `humanizer-en`은 쓰지 않는다(writing-pipeline 표).

```bash
npx -y -p textlint -p textlint-rule-write-good textlint --no-textlintrc --rule write-good src/content/blog/en/<이름>.md
```

- 직역 말투를 남기지 않는다. 의도한 약속 문구는 write-good에 걸려도 그대로 둔다.

### 9-3. 교정 뒤 대조

윤문 결과를 그대로 믿지 않고 두 언어 파일을 처음부터 다시 읽는다.

- 수치·날짜·고유명·한정어("이상", "최대", "할 수 있습니다")가 원문과 같은지, 영어판 숫자·이름이 한국어판과 같은지 본다. 강도가 바뀐 문장은 원문 쪽으로 되돌린다.
- 윤문이 만든 중복 문장(도입부에 같은 사실을 두 번 쓰는 경우 등)과 앞뒤가 끊긴 문단을 고친다.
- §6 금기 문장이 다시 생겼으면 지운다.
- 문장마다 §6-0으로 점검한다: 모양을 묘사하는가 쓸모를 말하는가, 수식어에 출처가 있는가, 날짜·시각이 이 글에 필요한가, 이야기 꾸밈 어휘가 없는가. 한 편에서 해당 문장을 하나라도 찾으면 같은 유형을 글 전체에서 찾아 고친다. 사용자가 지적한 문장만 고치고 끝내지 않는다.
- 문장 호흡을 잰다: `python3 .claude/skills/blog-auto-write/check-rhythm.py src/content/blog/ko/<이름>.md`. 평균 문장 길이, 40자 미만 비율, 짧은 문장이 3개 이어지는 구간을 알려 준다. 경고나 끊기는 구간이 나오면 그 문단을 §6 공통의 연결 어미 규칙으로 다시 잇는다. 숫자는 보조 신호이고, 합격 여부는 소리 내어 읽는 점검이 정한다(2026-11-06: Opus·Fable 초안 평균이 43자·49자였고 사용자는 Opus가 더 끊긴다고 느꼈다).
- 문단의 마지막 문장을 지워 보고 뜻이 그대로면 평가·요약·약속의 중복이니 지운다("재미있다고 꼽은", "바로 고치겠습니다").
- 소리 내어 읽듯 다시 본다. 같은 사실이 겹치는 문장, 보고서처럼 끊기는 나열, 같은 틀의 문장 반복이 남았으면 블로그 말투로 다시 잇는다(§6 첫 목록). 윤문 스킬은 AI 흔적만 고치고 이런 곳은 남기기 쉽다.
- 제목과 소제목만 뽑아 이어 읽는다(`grep -h '^title\|^## ' <파일>`). 결론문 목록이나 표어 모음처럼 읽히거나, 완결 문장 소제목이 둘 이상이거나, 같은 틀이 이어지면 §1-3·§6 소제목 규칙대로 다시 단다.
- 초안 점검: §3-3 표의 필수 요구가 모두 절·증거에 들어갔는지, 낯선 용어가 소개 없이 나오지 않는지, 근거 없는 효과 문장이 없는지, 방문객에게 필요 없는 내부 정보가 없는지 본다.
- 마지막으로 §0의 세 기준을 하나씩 따져 보고, 못 미치는 곳을 고친다. 판정마다 글 속 근거 문장을 하나씩 짚고, 판정과 고친 곳은 보고에 적는다.
- news에서 서법 경고(P5)가 난 문장은 보고에 적어 사용자가 정하게 한다.

### 9-4. 공개 적합성 (본문·코드·이미지·alt마다, 사용자 지시 2026-11-06 Codex 리뷰)

사실이 맞는지 보는 것(§9-3)과 공개해도 되는지 보는 것은 다르다. 이 글은 방문객 누구나 읽는다.

- 개인·계정·기기 식별 정보, 비밀값, 공개하지 않은 계획은 쓰지 않는다.
- 내부 작업 ID, 파일 경로, 폴더 이름은 설명에 꼭 필요할 때만 남긴다. 나머지는 예시 값으로 바꾸거나 뺀다.
- 아직 출시하지 않은 작품과 기능은 현재 단계와 기준일을 함께 쓰고, 이름은 사이트에 이미 공개된 것만 쓴다.
- 사용자가 실제 작업 자료의 공개를 승인한 글은 승인 범위 안에서 실제 자료를 쓴다. 비밀값·개인정보·계정 정보는 승인과 관계없이 뺀다. 승인이 없으면 스크린샷은 데모 데이터로 찍는다. 실제 데이터로 찍을 때는 읽기 전용 이동만 하고, 상태를 바꾸는 버튼을 누르지 않는다(2026-11-06에 점검 중 실제 작업 하나를 바꿔 되돌린 사고가 있었음). 화면에 보이는 이름과 문구를 하나씩 보고 공개해도 되는지 판단한다.
- 공개 여부가 불명확한 자료는 빼고 보고(§13)에 적는다. 사용자가 해당 자료의 공개를 명시적으로 승인하면 유지하고, 승인한 내용과 날짜를 보고에 적는다(예: 2026-11-06 개발기 글의 실제 작업명 스크린샷·옛 로드맵 예시는 사용자 승인으로 유지).

## 10. 빌드 (최대 3회)

```bash
npx astro build 2>&1 | tail -30
```

- frontmatter 위반(excerpt 길이, category, date, tags 수, coverAlt 누락) → 고치고 다시 빌드.
- `[blog] ... 없는 작품 slug` 경고 → works 값을 고친다.
- 내 파일과 무관한 빌드 오류 → 멈추고 보고.
- 3회 실패하면 멈추고 마지막 오류 30줄을 보여 준다. 파일은 지우지 않는다.

## 11. 커밋과 미리보기

```bash
git add src/content/blog/ko/<이름>.md   # 영어판·표지는 실제로 만든 경우에만 경로를 덧붙인다
git commit -m "post: <제목>"
npx astro preview --port 4329   # run_in_background로 띄운다
open -a Aside http://localhost:4329/blog/<이름>/
```

- 경로를 하나씩 지정해 add한다. 만든 파일만 넣는다(영어판 `src/content/blog/en/<이름>.md`, 표지 `src/assets/blog/<이름>/cover.jpg`). 없는 경로를 넣으면 add가 실패한다. `.omc/`는 넣지 않는다.
- 미리보기에서 한국어·영어 모두 목차, 표, 코드, 이미지가 읽히는지 확인한다. 모바일 폭(390px)에서 가로 스크롤이 생기지 않는지, 이미지가 모두 불러와지는지(지연 로딩은 끝까지 스크롤해서 확인) 포함한다. 빌드 성공은 편집 품질 확인을 대신하지 않는다.
- 이 단계에서는 push하지 않는다.

## 12. 공개 (사용자가 "올려"라고 한 뒤에만)

```bash
git -c credential.helper= -c 'credential.helper=!gh auth git-credential' push -q origin HEAD:main HEAD:astro-site
gh run list -R waveworkscorp/waveworkscorp.github.io -L 1
```

- 배포 실행이 success가 되면 공개 주소(`https://waveworkscorp.github.io/blog/<이름>/`)를 알린다.
- 미리보기 서버를 끈다.

- 파일 경로(ko, en, 표지)

- §0 세 기준 판정(마케팅·브랜딩, 사람 문체, 읽기 쉬움)과 근거 한 줄씩
- 표지 생성 여부, 본문 그림 수와 출처
- 문체 교정 결과(언어별로 돌린 스킬, 자연도 등급, 검사 지적 수, 대조에서 되돌린 곳)
- 공개 적합성 점검 결과(§9-4)에서 뺀 자료와 남긴 내부 정보
- 사실 출처 목록(문장 → 파일)
- 빌드 재시도 횟수, 커밋 SHA, 미리보기 주소
- 실제 자료 공개 승인을 근거로 쓴 자료는 승인 날짜, 사용자 지시 원문, 글 slug, 대상 이미지·코드, 제외한 범위를 적는다. 승인 뒤에 자료를 더하거나 범위를 넓힌 부분은 다시 검토했다고 밝힌다. 자료 공개 승인과 push 승인은 별개이고, 한쪽이 다른 쪽을 대신하지 않는다.
- 교정 보고는 도구를 실제로 호출한 것, 정상 완료한 것, 결과를 반영한 것, 도구 없이 직접 점검한 것으로 나눠 적는다. 도구가 내놓지 않은 자연도 등급은 적지 않는다.
- 공개 승인 요청은 AskUserQuestion으로 묻는다("올려" / "고칠 곳 있음").
